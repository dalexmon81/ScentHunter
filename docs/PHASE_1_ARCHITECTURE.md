# Phase 1 — repository, backend and PostgreSQL foundation

## Starting point

Phase 0 is closed. Its live baseline CSV was downloaded from GitHub Actions run #49.
The current production backend is still a single FastAPI entry module backed by a
SQLite catalog on the Fly volume. The isolated `backend/scenthunter_next_engine`
package contains domain models and catalog identity/matching work, but is not yet
the production persistence layer.

## Phase 1 guardrails

- Keep production search and the existing SQLite volume unchanged until a tested,
  reversible data migration and parity checks are complete.
- Do not mix retailer listings with canonical product identity.
- A retailer product URL is the discovery/hydration unit; multiple sizes on that
  page remain separate offer variants.
- Only an explicit `matched` decision may carry canonical product and variant IDs.
- Keep discovery and hydration queues separate.
- Do not delete operational diagnostics until their value and replacement are
  established. Remove generated bytecode and build artefacts from source control.
- Make changes on `phase-1/backend-postgres-foundation`; merge only after tests,
  migration validation, and a documented rollback.

## Work sequence

### 1. Repository hygiene
1. Add ignore rules for Python caches, virtual environments, local databases,
   test caches, generated reports and local secrets.
2. Remove already-tracked Python bytecode.
3. Inventory diagnostic scripts and JSON catalog snapshots; classify each as
   runtime input, test fixture, reproducible output or obsolete before moving it.
4. Keep the production Docker build inputs explicit.

### 2. Backend separation
1. Extract configuration and database lifecycle from `backend/main.py`.
2. Move route groups into focused FastAPI routers (health, search, catalog,
   administration and retailer operations).
3. Move orchestration/background workers out of route modules.
4. Preserve existing route paths and response contracts during extraction.
5. Add focused tests around each extracted boundary before removing old code.

### 3. PostgreSQL foundation
1. Establish the normalized PostgreSQL schema in
   `backend/migrations/postgresql/0001_initial_schema.sql`.
2. Build a repository adapter behind the existing catalog interface.
3. Add a read-only SQLite-to-PostgreSQL comparison/import tool with counts,
   duplicate checks, invalid-row reports and resumable checkpoints.
4. Validate identity, price, URL, stock and queue parity on a production-sized
   copy before any traffic cutover.
5. Cut over only after explicit approval; retain SQLite rollback data.

## Schema mapping

| Existing SQLite concept | PostgreSQL target |
|---|---|
| `store_urls` | `retailer_products` |
| `store_products` | `retailer_offers` |
| `store_product_variants` | `retailer_offer_variants` |
| `sync_state` | `retailer_sync_state` |
| `catalog_discovery_queue` | `catalog_discovery_queue` |
| `hydration_queue` | `hydration_queue` |
| `hydration_scheduler` | `hydration_scheduler` |
| `catalog_coverage` | `catalog_coverage` |
| canonical `product_catalog.json` | `canonical_products`, `canonical_variants` and alias tables |

## Current boundary

Migration 0001 creates the target tables only. It does not import the current
catalog, change `SCENTHUNTER_CATALOG_DB`, require a production Postgres instance,
or alter Fly deployment. The next implementation step is a tested repository
adapter and a dry-run migration tool, not a production cutover.
